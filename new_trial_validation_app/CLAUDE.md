# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the **new** Laravel app replacing the legacy PHP app at the repo root (`../`). See `../CLAUDE.md` and `../MIGRATION_PLAN.md` for the overall migration plan, phase checklist, and SSO bridge design — this file only covers commands/architecture local to this Laravel codebase.

## Commands

```bash
composer run dev      # php artisan serve + queue:listen + vite dev, all concurrently
composer run lint      # pint --parallel (auto-fix)
composer run lint:check   # pint --parallel --test (check only)
composer run types:check  # phpstan analyse (larastan)
composer run test      # config:clear + lint:check + types:check + php artisan test
composer run ci:check   # npm lint:check + npm format:check + npm types:check + test

php artisan test                                  # full Pest/PHPUnit suite
php artisan test --filter=TestName                # single test by name
php artisan test tests/Feature/DashboardTest.php   # single file

npm run dev          # vite dev server (frontend only, use alongside `php artisan serve` if not using composer run dev)
npm run build         # vite build (add build:ssr for SSR build)
npm run lint          # eslint --fix
npm run format         # prettier --write resources/
npm run types:check      # tsc --noEmit
```

Tests use **Pest** (`tests/Pest.php`), not raw PHPUnit syntax, even though `phpunit.xml` configures the runner.

## Architecture

Official `laravel/react-starter-kit` scaffold — **Inertia.js**, not a decoupled REST API + SPA. Pages are server-rendered React components returned via `Inertia::render()` from controllers in `app/Http/Controllers`; there is no client-side router fetching JSON from a separate API for these pages.

- `resources/js/pages/` — Inertia page components (one per route), grouped by feature (`auth/`, `settings/`).
- `resources/js/layouts/` — shared layout shells (`app/`, `auth/`, `settings/`).
- `resources/js/components/ui/` — shadcn/Radix UI primitives.
- `resources/js/routes/` and `resources/js/actions/` — **generated by Laravel Wayfinder** (`laravel/wayfinder` + `@laravel/vite-plugin-wayfinder`), giving typed TS helpers for Laravel routes/controller actions. Don't hand-edit these — they regenerate from PHP routes/controllers on build.
- `app/Actions/Fortify/` — Laravel Fortify handles auth actions (registration, password reset, etc.); `app/Providers/FortifyServiceProvider.php` wires it up.
- `routes/web.php` / `routes/settings.php` — current routes are all Fortify/starter-kit boilerplate (profile, security settings) — no trial-validation domain routes exist yet.
- `boost.json` / `.mcp.json` — Laravel Boost is configured, providing MCP tools for this Laravel app (schema/route/log introspection etc.) when available in this session.

### RBAC / authorization (ported from legacy `bootstrap.php`, 2026-08-24)

`app/Models/User.php` maps onto the **real** shared `users` table (`password_hash`, `role`, `department`, `is_active` — no `password`/`email_verified_at`/`remember_token`/`updated_at`), not the starter kit's default schema; the fresh-install migration branch (used by sqlite/tests) was changed to match this same shape so behavior is identical in every environment. It carries role/department helper methods (`isAdmin()`, `isStaff()`, `isReviewer()`, `reviewDepartmentsForUser()`, etc.) ported from `is_admin()`/`is_staff()`/`is_reviewer()`/`reviewer_department_codes()` in the legacy app.

`app/Models/Trial.php`, `TrialReview.php`, `TrialEditPermission.php`, `MasterOption.php` are minimal stubs mapping onto the shared `trials_header`/`trials_review`/`trial_edit_permissions`/`master_options` tables — just enough for the RBAC port below; Fase 1 (Masters) and Fase 3 (trial workflow) will flesh them out with real CRUD/relations.

`app/Policies/TrialPolicy.php` ports `can_view_trial()`/`can_edit()`/`can_approve_trial()` (`view`/`update`/`approve` abilities — auto-discovered by Laravel via the `Trial`/`TrialPolicy` naming convention, no manual registration needed). `Trial::scopeVisibleTo()` ports the row-level list-scoping query from `scoped_trials_parts()` — use it wherever a trials list needs to be restricted to what the current user may see. Simple admin-only checks that aren't tied to a model instance (`can_manage_master()` etc.) are registered as Gates in `AppServiceProvider::configureGates()` (`manage-settings`, `manage-master`, `manage-parameters`, `view-products-template`, `manage-templates`).

### Fase 1 progress

**Users** (2026-08-24): `app/Http/Controllers/Admin/UserController.php` (`admin.users.index/store/destroy`, routed from `routes/admin.php`) + `resources/js/pages/admin/users/index.tsx` — list/search, create-or-update-by-email upsert (mirrors legacy's single "Save / Change Password" form), soft delete. `app/Policies/UserPolicy.php` gates it (viewAny/create/update/delete), including the Super-Admin-target protection rules from legacy. `User::roleCategories()` ports `role_categories()`.

Two gotchas hit while building this, relevant to any future model-mutating controller code:
- `User`'s `#[Fillable(['name','email','role','department'])]` attribute deliberately excludes `password_hash`/`is_active`/`deleted_at`/`deleted_by`. Mass-assignment helpers (`updateOrCreate`, `Model::update([...])`) silently drop those fields with no error — set them via direct property assignment (`$user->password_hash = ...; $user->save();`) instead.
- `AppServiceProvider::configureDefaults()` rebinds the `Date` facade to `CarbonImmutable` app-wide, so the `now()` helper returns a `CarbonImmutable`. Assigning that to a property typed as `Carbon` (e.g. `deleted_at`) fails Larastan. Use `\Illuminate\Support\Carbon::now()` explicitly for those assignments.

Legacy's Access Rights screen was deferred at the time this was written — it's since been built, see below.

**Products** (2026-08-24): `app/Http/Controllers/Admin/ProductController.php` (`admin.products.index/store/destroy`, routed from `routes/admin.php`) + `resources/js/pages/admin/products/index.tsx` — paginated list, edit-in-place via `?edit={id}`, create-or-update-by-id-or-name upsert, soft delete. No new Policy — reuses the `manage-templates` Gate from `AppServiceProvider::configureGates()` (Admin or Staff). New `App\Models\Product` maps onto the real shared `products` table (`product_name` unique, `finish_good_code`, `is_active`, `deleted_at`, `deleted_by` — no timestamp columns); its fresh-install migration follows the same `Schema::hasTable` guard pattern as the `users` migration. `finish_good_code` is plain free-text in legacy, no auto-generation logic — confirmed before porting.

**Parameters** (2026-08-24): `app/Http/Controllers/Admin/ParameterController.php` (`admin.parameters.index/store/destroy`, routed from `routes/admin.php`) + `resources/js/pages/admin/parameters/index.tsx`, linked from `app-sidebar.tsx`. No new Policy — reuses the `manage-parameters` Gate (Admin or Staff), same shape as `manage-templates`. New `App\Models\ValidationParameter` maps onto the real shared `validation_parameters` table (`product_type`, `parameter_name`, `specification`, `sort_order`, `is_active`, `deleted_at`, `deleted_by` — no timestamps); its fresh-install migration follows the `products` pattern. Unlike Products, legacy's save here is a plain create-or-update-by-id — there's no upsert-by-name matching, so saving without an `id` always inserts (even on a duplicate `parameter_name`); the port preserves that.

The product-type dropdown on this page reads `master_options` (`type='product_type'`) through the existing `App\Models\MasterOption` stub — this is what finally required adding `2026_08_24_000003_create_master_options_table.php`, a fresh-install migration for `master_options` (schema-only, same shared-DB-skip guard as the other tables). That table had no migration until now even though `User::reviewerDepartmentCodes()`/`roleCategories()` already queried it from the Fase 0 RBAC port — they just never hit a fresh sqlite install without a try/catch fallback masking the gap. This migration does **not** front-run the separate Masters CRUD module (still unbuilt) — it only makes the table exist.

Also added `resources/js/components/ui/textarea.tsx` (shadcn primitive, wasn't in this scaffold yet — needed for the Specification field).

**Access Rights** (2026-08-24): `app/Http/Controllers/Admin/AccessRightController.php` (`admin.access-rights.*` in `routes/admin.php`) + `resources/js/pages/admin/access-rights/index.tsx`, linked from the sidebar (Super Admin only, unlike the Admin-or-Staff modules above). Ports legacy's `/admin/access-rights` block in full: user role/department reassignment (edit-in-place via `?edit={id}`, same pattern as Products/Parameters, since a per-row `<Form>` can't legally nest inside a `<table>`), reviewer-department master CRUD against `master_options` (`type=reviewer_department`), and draft-trial edit-permission grant/revoke against `trial_edit_permissions`. New `manage-access-rights` Gate in `AppServiceProvider` (`isSuperAdmin()`, no Admin fallback — unlike every other Gate in this file). Three Form Requests (`UpdateUserRoleRequest`, `StoreReviewerDepartmentRequest`, `GrantDraftPermissionRequest`).

Two schema gaps surfaced while building this — neither table had ever gotten a fresh-install migration despite `App\Models\Trial`/`TrialEditPermission` existing as Fase-0 stubs, because nothing had exercised them against a fresh DB yet:
- Added `2026_08_24_000004_create_trials_header_table.php` (minimal columns matching `Trial`'s existing `#[Fillable]` list, same shared-DB-skip guard pattern as the others) and `2026_08_24_000005_create_trial_edit_permissions_table.php` (matches `../../database/20260702_trial_edit_permissions.sql` exactly).
- Added `TrialEditPermission::grantedBy()` (`BelongsTo<User>` on `granted_by`) alongside the existing `trial()`/`user()` relations, for the draft-permission list's "granted by" column.
- Added a `unique(type, name)` index to `master_options` in its fresh-install migration (`2026_08_24_000003_...`) — no legacy migration file was found that actually creates this constraint, despite legacy's reviewer-department save relying on `ON DUPLICATE KEY UPDATE` (which needs one to make sense). The port doesn't depend on the DB constraint either way — `storeReviewerDepartment()` does an app-level `firstWhere()`-then-save instead of a raw upsert, so this index is just defensive, not load-bearing.

16 new Pest tests (role reassignment incl. self-edit block and unknown-role rejection, reviewer-department upsert/soft-delete/undelete, grant/revoke incl. owner-already-has-access and non-Draft/non-Staff rejection, re-grant-after-revoke reactivation); full suite, Pint, Larastan, ESLint, Prettier, tsc, `npm run build` all pass. Live-spot-checked via `php artisan serve` + scripted login as `admin@local.test` (promoted to Super Admin for this, per `../CLAUDE.md`'s 2026-08-24 incident note) — renders correctly against real restored data (42 users, 6 Draft trials, 7 Staff users).

**Masters** (2026-08-26): `app/Http/Controllers/Admin/MasterOptionController.php` (`admin.masters.index/store/destroy`, routed from `routes/admin.php`) + `resources/js/pages/admin/masters/index.tsx`, linked from `app-sidebar.tsx`. No new Policy — reuses the `manage-master` Gate (Admin or Staff), same shape as `manage-templates`/`manage-parameters`. Uses the pre-existing `App\Models\MasterOption` stub and its migration (both already existed, added during the Parameters/Access Rights work) — no schema changes needed this time.

Live-spot-checked (read-only — no writes made against the shared DB) via `php artisan serve` + scripted login as `admin@local.test` (Super Admin) — 200 OK, 122 real master options across 7 paginated pages, correctly ordered by type/sort_order/name; no `role_category`/`reviewer_department` rows exist in the shared DB yet, so the privileged-type-visible-to-Super-Admin path wasn't observable live, only test-covered.

### Reconciling with MIGRATION_PLAN.md

`../MIGRATION_PLAN.md` §5 was drafted assuming a pure JSON API (Sanctum token/cookie auth + API Resources) for *every* screen, to keep the web and future mobile app on the same contract. This scaffold being Inertia-based changes that for the web side:

- Web pages → `Inertia::render()` from normal controllers, authenticated via standard Laravel session (Fortify) — this is actually simpler than the original plan's cookie-based Sanctum SPA setup, and the SSO bridge design (ticket → `Auth::login()`) still applies unchanged.
- Mobile app (Fase 4+) will still need a separate `/api/v1/*` namespace with Sanctum **token** auth and API Resources, since Inertia responses aren't consumable by a mobile client.
